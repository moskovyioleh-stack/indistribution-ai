# Исправление Tilda MCP gateway

Самостоятельная реализация требований от 30.10.2026 на основе
33b5e368229a2e31ef46dffeffab130e746c1950. Не воспроизводит недоступный
patch/локальный commit c31dbef. Предыдущие 46 тестов не относятся к этой реализации.

## Маршруты и разрешения

Основной интерфейс: editor_action(action="tilda_call", payload=...).
Браузерная сессия не требуется. Необязательный inspect использует другой путь.
capabilities версии 1.1 разделяет native gateway, браузер и нереализованные UI-действия.
Описание инструмента изменено в коде сервера. Уже подключённый клиент может
кэшировать старое описание до обновления списка MCP tools.

Проекты операций: 12112685, 14178377, 23291206, 30763609.
add_blank_page: 14178377, 23291206, 30763609; только projectid, без публикации.
Список операций записи фиксирован в NATIVE_WRITES и не расширяется по upstream.
Существующие ограничения форм, списков карточек, шрифтов, favicon, head и Zero Block
сохранены. Псевдонимы send_key не позволяют обойти ограничения защищённых списков.

Старый tilda_remove_draft_block запрещён до любой работы с upstream, его
реализация удаления удалена. Старый tilda_create_draft_page больше не создаёт
ресурсы в обход основного gateway: возвращает redirect_required и указание
использовать tilda_call/add_blank_page. Это явное изменение legacy-контракта.
Остальные legacy-маршруты не переведены на новый контракт статусов.

## Целевые изменения полей

update_record: обязательны projectid, pageid, recordid, tab, only_field,
fields ровно с одним ключом. В payload обязательны confirmation=SAVE_DRAFT_ONLY
и expected_old_value, включая допустимую пустую строку. Отсутствие/null запрещены.
Непосредственно перед записью gateway читает edit_record той же вкладки.
Редактируемое поле определяется по fields и документированному send_key;
неоднозначная, неизвестная, hidden/read-only схема отвергается. Только документированное
пустое поле может отсутствовать в record. Сравнение рекурсивно сохраняет типы,
пробелы и регистр. Boolean не равен integer.

Пример payload:

    {
      "tool": "update_record",
      "arguments": {
        "projectid": 30763609, "pageid": 187658209, "recordid": 3056787401,
        "tab": "settings", "only_field": "title_tag",
        "fields": {"title_tag": "h2"}
      },
      "expected_old_value": "",
      "confirmation": "SAVE_DRAFT_ONLY"
    }

update_page_settings: IDs, исходная date в формате YYYY-MM-DD HH:MM и ровно одно
поле из существующего безопасного списка. Перед записью get_page_settings
должен подтвердить исходную дату и точное expected_old_value поля.
Пример: arguments с meta_title и датой плюс expected_old_value старого meta_title
в payload. Несколько SEO-полей за один вызов больше не поддерживаются.
Служебные expected_old_value/confirmation в arguments отвергаются; upstream
получает только параметры официального метода.

Это оптимистическая проверка, а не транзакционный CAS на стороне Tilda:
внешнее изменение между чтением и записью нельзя полностью исключить.

## Результаты

- draft_verified: повторное чтение подтвердило точное сохранённое значение.
- verification_mismatch: повторное чтение показало другое значение; без повторной записи.
- write_unconfirmed: запись была вызвана, но её результат/проверка неопределённы.
  Сначала проверить фактическое состояние, не повторять автоматически.
- upstream_error/precondition_failed до записи: поле не записывалось.
- upstream_accepted для остальных разрешённых операций означает только принятие
  запроса, не проверку сохранения и не публикацию.

Проверяются MCP is_error/isError, JSON-текст, structured_content и стандартные
вложенные error/result/data/response envelopes. Тексты ошибок/секреты не возвращаются
из обработчика исключений. Автоматических повторов записи и создания нет.

## Дополнительное чтение

get_project_settings, get_sitemap_xml, page_preview, describe_tool включены в
фиксированный набор OPTIONAL_READS. Каждый вызов проверяет наличие метода и
его inputSchema в текущем upstream-каталоге. При отсутствии - unsupported_method.
Аргументы ограничены точной формой; project/page проверяются на принадлежность.
describe_tool принимает только существующее имя инструмента и не выполняет его.
get_record_html и include_html:true у get_page_records сохранены.

## Тестирование и релиз

Команда: python -m unittest discover -s tests -v.
Тесты вызывают реальный register_bridge/editor_action с mocked fastmcp upstream.
В минимальной локальной среде только импорт JSONResponse заменён тестовым stub,
если Starlette отсутствует; зависимости production не заменяются.
Нет сетевых вызовов, реальных тестовых страниц и публикаций.

Сценарии: пустое/непустое значение, missing/null, конфликт, whitespace/types,
send_key и его неоднозначность, неизвестные поля, один target, подтверждение,
чужие проекты/страницы/блоки, создание HEINEDA, запреты удаления и публикации,
специальные ограничения, structured errors, readback error/mismatch и отсутствие retry.
Фактическое число и результат собственного запуска указать в отчёте релиза.

## Production-проверка

Цель Railway: precious-tenderness / indistribution-ai-editor /
service 32116d5e-8244-4a60-b24d-deb81a3a4c5e /
environment 2fc0d76e-4013-491d-84fd-f703b9c06667.
Ветка feature/tilda-editor; основной indistribution-ai использует main.
Перед push повторно проверить HEAD и отсутствие смены привязки.

После успешного деплоя сверить deployed commit, /healthz и capabilities.
Health показывает draft_only, publishing_allowed=false, editor_api_version
и RAILWAY_GIT_COMMIT_SHA, если штатная переменная предоставлена платформой.
Не менять переменные окружения ради этой проверки.

Через действующий editor_action проверить четыре дополнительных read-метода.
Не выводить персональные данные get_project_settings/page_preview.
Затем подтвердить HEINEDA через get_projects и прочитать baseline:
настройки страницы 187658209, content/settings/HTML блока 3056787401,
таблицу 3056702901 и остальные блоки страницы.

Только если заголовок остаётся «Основные технические характеристики», поле
title_tag документировано и пусто, сохранить h2 одним вызовом.
Если уже h2 - ничего не записывать. При расхождении содержания/схемы/другом
значении остановить эту запись. Повторно прочитать настройки и HTML,
сравнить текст, оформление, таблицу и published. Ничего не публиковать.

При неоднозначном ответе после записи сначала читать состояние, не повторять её.
После результата релиза сохранить отдельный отчёт с commit/deployment и проверками.
